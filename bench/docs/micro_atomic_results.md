# 마이크로벤치 결과 — failure-atomic write() 의 비용과 확장성 (run atomic_20260921_0055)

상태: **1 차 실행 완료** (6 FS × 26 셀 = 156 셀) + 후속 (a)~(e) 완료.
원자료 2: `results/micro/followup_20260921_0246/summary.csv`, `followup_e_20260921_0312/summary.csv`.
계획: `osdi_experiment_plan.md` §1.2 / §1.4 / §1.5. 하네스: `bench/workspace/tools/micro_atomic.sh`.
원자료: `bench/workspace/results/micro/atomic_20260921_0055/summary.csv` (scratch 디렉터리 — 인용 시 재실행 후 named 디렉터리로).

## 0. 결론

1. **rename 대체 논거는 성립.** 4 K 단일 fsync overwrite 에서 tau 는 ext4-dj(전역 data=journal)보다
   1.15x(ext4 seam) / 1.5x(XFS seam), btrfs(CoW)보다 4~5x 빠르고, 장치 증폭은 3.6 vs 4.1 vs **49.7**.
   64 K 이상에서는 베이스라인의 90~100 %(XFS 에서는 초과).
2. **tau 의 비용은 seam 과 무관.** ext4-tau 와 xfs-tau 가 16 K 이상 overwrite · same_N · multi_N ·
   append 전 셀에서 같은 숫자(증폭 1.67 / 1.17 / 1.04 까지 동일). 4 K 만 갈리며(14.3 k vs 18.8 k)
   그 차이는 ext4 의 fsync 마다 얹히는 jbd2 inode 커밋 몫.
3. **확장성 한계 둘**: (a) 같은 파일 N writer 에서 평평(20 k 고정; ext4/xfs 는 group commit 으로
   200 k+), (b) 다중 파일에서 ~125 k ops/s 상한 + N≥16 에서 초 단위 스톨(12~16 s).
3b. **multi_N 상한은 장치 대역폭**: 64 K 에서 tau 35 k ops/s = 2.2 GB/s(장치 2.5 GB/s), 4 K 에서 125 k = 1.9 GB/s 장치.
   fsync 횟수 상한이 아니다. tau/ext4 비율이 4 K 30 % → 64 K 66 % 로 오르는 것은 증폭(3.8 → 1.14) 차이.
3d. **병합은 실재한다**: hot set 16 M 에서 drain 포함 tau 총량 1.16 (fe=64) / 1.02 (fe=1024) vs ext4-dj
   2.03 / 1.78 — superseded 사본이 제자리로 가지 않는다. 처리량 1.7~2.8x. §1.4 예측 적중.
3c. **진짜 증폭(drain 포함, hot set 없음) = ext4-dj 와 동급**: 4 K 4.36 vs 4.09, 16 K 2.40 vs 2.53, 64 K 2.02 vs 2.14.
   바이트가 아니라 경로가 이점(같은 셀 모양에서 19.5 k vs 11.4 k ops/s) — §4.19 의 메인벤치 결론 재현.
4. **append 하한**: 4 K fsync=1 에서 ext4-tau ≈ ext4(1.03x), xfs-tau 0.90x. 64 MB/fsync 에서 0.61~0.86x
   (저널 대역폭 한계, 분할 문제 아님 — p50 29 ms 는 모든 FS 공통 = 64 MB 쓰기 시간).
5. **CoW aging 축은 이 규모에서 무의미**: btrfs pass1→aged 3.1 k→3.6 k. 16 GB 파일에 2 GB 랜덤
   overwrite 는 첫 패스부터 이미 조각남. 축을 빼거나 규모를 키워야 한다.

## 5. 절차 결함 (v2 하네스 반영)

- **첫 셀 warm-up 오염**: xfs 4 K pass1 10.6 k → aged 31.0 k, ext4-dj 8.4 k → 12.5 k, ext4-tau
  11.4 k → 14.3 k. 각 FS 의 첫 셀 앞에 warm-up 필수. 이 문서는 aged 패스를 인용.
- `amp` 는 셀 구간만: tau 의 제자리 사본 미포함(§6 a 로 보정).
- `jwrite_blocks` 프로브가 큰 write 에서 ~37 % 과소(별도 확인 필요).
- **`tauoverwrite` 고정 시드(`srandom(12345)`)**: same_N/multi_N 의 N 프로세스가 같은 offset 열을 썼다.
  fe=1 인 v1 에서는 장치 증폭이 정상(ext4 1.00, tau 3.5)이라 결과는 유효하나 hot set 이 16 GB 가 아니라
  200 k 페이지(800 MB)로 좁아진 confound 가 있다. fe=64 에서는 페이지 캐시 병합으로 amp 0.25 가 되어
  치명적(v2 첫 시도 폐기, `atomic2_20260922_aborted_sameseed`). 2026-09-22 `TAU_SEED` 환경변수 추가
  (기본값 12345 유지 — tautest 스위트 호환), 하네스는 프로세스마다 `12345+i`.
- 장치 flush 카운터 사용 불가(0). fsync 당 FLUSH 수는 다른 방법(blktrace) 필요.
- 이전 시도 3 회 실패 원인: iostat 첫 샘플(부팅 평균) → sysfs delta 로; multipath head stat = 0
  → 경로 장치 합산; bash `local a=$(..) b=${a..}` 한 줄 확장 순서 → 줄 분리.

- **fsync 를 묶으면 tau 가 plain ext4 보다 빠르다**: fe=64 에서 180 k vs 163 k, fe=1024 에서
  264 k vs 182 k(16 G). ext4 의 fsync 는 64/1024 개 랜덤 제자리 쓰기 + jbd2 커밋인데 tau 의
  커밋은 순차 저널 쓰기 하나이고 제자리는 뒤로 미뤄진다. 이것이 §4.19 "WAL 403 → 35 MB/s"
  의 마이크로 형태 — **fsync 경로가 순차화된다**.

  dirty 페이지만 저널에 간다. ext4-dj 는 그 2 배(1.78). 제자리까지 포함한 tau 총량은 (e).
- 256 M/fe=1 의 tau 저하(19.6 k → 14.7 k, p99 0.075 → 0.358 ms)는 16 M 에서 재현되지 않음(19.7 k).
  단일 셀 노이즈 가능 — 재실행 전에는 인용 금지.
- `jwrite_blocks` 프로브는 fe≥64 에서 저널 바이트를 크게 과소(16 G/fe=64: 373 MB vs 장치 ~2.1 GB).
  프로브 정의 확인 필요 — 지금은 장치 바이트만 신뢰.

### (e) 병합 곡선, drain 포함 — 병합의 증거

셀 + sync + umount 까지의 장치 바이트 (fresh mkfs + warm-up 65536 op/셀):

| hot set / fe | ext4-dj ops/s \| amp | ext4-tau ops/s \| amp (저널 / 제자리 MB) |
|---|---|---|
| 16 G / 64 | 88,982 \| 2.04 | 149,248 \| **1.83** (≈2,100 / ≈1,650) |
| 16 M / 64 | 84,386 \| 2.03 | 233,563 \| **1.16** (≈2,100 / 254) |
| 16 M / 1024 | 154,471 \| 1.78 | 370,279 \| **1.02** (≈1,800 / 254) |

- **tau 의 총 바이트는 hot set 이 작아질수록 1.0 으로 내려가고 ext4-dj 는 2.0 에 머문다.** 16 M/fe=64:
  hot set 4,096 페이지가 128 번 재기록되는데 제자리에는 16 번 분량(254 MB)만 갔다 — superseded 사본은
  체크포인트되지 않고 revoke 된다(anchor→revoke). jbd2 data=journal 은 커밋마다 저널 1x 에 제자리 1x
  를 그대로 더한다.
- 처리량도 1.7~2.8x (149 k vs 89 k, 234 k vs 84 k, 370 k vs 154 k) — 병합 + 순차 커밋의 합.
- 이것이 §4.19 의 "저널 ≈ FPI 바이트지만 제자리는 줄어든다" 의 마이크로 재현이며, **§1.4 예측(hot set 이
  작을수록 1x)이 맞았다.**
- 주의: 16 G 셀에서 제자리 ≈1,650 MB < 고유 데이터 ≈1,930 MB. umount 가 저널을 완전히 비우는지
  (또는 남은 사본을 다음 마운트의 replay 에 맡기는지) 확인 필요 — `tau_probe_flush_submit` 1,614 MB 도
  같은 값이라 프로브 문제는 아님.
- (b)/(e) 의 저널 프로브(`jwrite_blocks`)는 장치 바이트에서 역산한 값의 절반 이하로 나온다 — 프로브
  정의 확인 전까지 표의 저널/제자리 분해는 장치 총량 − 제자리 프로브로 읽을 것.
